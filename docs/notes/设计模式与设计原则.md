# DeerFlow 设计模式与设计原则

> 分析 DeerFlow 代码库中使用的设计模式与设计原则，帮助理解项目架构决策。

---

## 一、创建型模式 (Creational Patterns)

### 1.1 工厂模式 (Factory Method)

DeerFlow 大量使用工厂函数来解耦对象的创建与使用：

| 工厂 | 位置 | 作用 |
|------|------|------|
| `make_lead_agent()` | `agents/lead_agent/agent.py` | LangGraph 图工厂，注册于 `langgraph.json` |
| `create_chat_model()` | `models/factory.py` | 根据配置反射实例化 LLM |
| `make_checkpointer()` | `runtime/checkpointer/` | 检查点存储工厂 |
| `make_stream_bridge()` | `runtime/stream_bridge/` | StreamBridge 实例工厂 |
| `resolve_variable()` | `reflection/__init__.py` | 根据类路径字符串动态加载任意对象 |

核心模式：**通过字符串配置映射到运行时对象**，实现零代码修改的扩展。例如 `config.yaml` 中的 `models[].use: "deerflow.models.vllm_provider:VllmChatModel"` 驱动 `resolve_variable()` 动态加载。

### 1.2 构建者模式 (Builder)

将复杂对象的构造过程分步封装：

- `build_run_config()` (`app/gateway/services.py`) — 逐步组装 RunnableConfig，合并 thread_id、context、metadata、agent_name
- `build_lead_runtime_middlewares()` / `build_subagent_runtime_middlewares()` — 按固定顺序组装 8 个基础中间件
- `_build_middlewares()` (`agents/lead_agent/agent.py`) — 在前者基础上追加 10 个 lead-agent 专属中间件，形成完整的 18 层链
- `merge_run_context_overrides()` — 逐步将 context 覆盖合并到 config 的两个不同位置（configurable + context）

### 1.3 单例模式 (Singleton)

有状态但全局唯一的资源通过缓存函数管理：

- `get_app_config()` — 缓存 `AppConfig`，但通过 mtime 检测自动热重载
- `get_sandbox_provider()` — 缓存 `SandboxProvider` 实例，`_default_sandbox_provider` 模块级全局变量
- `RunManager` — Gateway 进程中作为 `app.state` 的单例注入

与经典单例的区别：不使用 `__new__` 或 metaclass，而是通过**依赖注入容器**（FastAPI `app.state` + 请求级 getter 函数）管理生命周期。

## 二、结构型模式 (Structural Patterns)

### 2.1 桥接模式 (Bridge)

**StreamBridge** (`runtime/stream_bridge/base.py`) 是典型桥接模式：

- **抽象接口**：`StreamBridge` 定义 `publish / publish_end / subscribe / cleanup`
- **实现分离**：agent worker（生产者）调用 `publish`，SSE endpoint（消费者）通过 `subscribe` 接收
- **独立演化**：生产者和消费者不直接耦合，通过桥接对象交互

LangGraph Platform 官方架构即是如此设计：Queue（生产） + StreamManager（消费）分离。

### 2.2 适配器模式 (Adapter)

将外部 API 适配到 LangChain 工具接口：

| 适配器 | 外部系统 | 适配为目标 |
|--------|---------|-----------|
| `tavily/` | Tavily Search API | LangChain `BaseTool` |
| `jina_ai/` | Jina Reader API | LangChain `BaseTool` |
| `firecrawl/` | Firecrawl API | LangChain `BaseTool` |
| `ddg_search/` | DuckDuckGo | LangChain `BaseTool` |
| `AioSandbox` | Docker SDK | `Sandbox` 抽象接口 |
| `VllmChatModel` | vLLM OpenAI-compatible API | LangChain `ChatOpenAI` 子类 |
| Slack / Feishu / Telegram / DingTalk | 各 IM 平台 API | `Channel` 抽象基类 |
| MCP adapter | MCP 服务器 | LangChain `BaseTool`（通过 `langchain-mcp-adapters`） |

适配器层次分明：`Channel` 基类定义 `start / stop / send` 生命周期，每个 IM 平台各自实现平台 API 调用逻辑。

### 2.3 代理模式 (Proxy)

控制对真实对象的访问：

- `SandboxMiddleware` — 代理 Sandbox 的 acquire/release 生命周期，延迟初始化（lazy_init），在首次工具调用时才获取沙箱
- `SubagentExecutor` — 代理子代理的后台执行，管理线程池 + 任务队列 + 状态报告
- `RunManager.cancel()` — 通过 `abort_event` 代理向运行中的任务发送取消信号
- `GuardrailMiddleware` — 在每个工具调用前插入授权检查层
- `UploadsMiddleware` — 代理上传文件的注入逻辑

### 2.4 外观模式 (Facade)

为复杂子系统提供统一入口：

- `DeerFlowClient` (`client.py`) — 统一的嵌入式客户端 API，封装 agent 创建、中间件组装、流式处理等内部细节。提供了与 Gateway REST API 一一对应的 `chat / stream / list_models / list_skills` 等方法
- Gateway API 层整体上也是 Runtime 的外观

### 2.5 依赖注入 (Dependency Injection)

运行时的依赖关系通过注入而非硬编码管理：

- Gateway 层：`get_run_manager(request)`、`get_stream_bridge(request)`、`get_checkpointer(request)`、`get_feedback_repo(request)` — 从 FastAPI `Request.app.state` 获取单例
- 配置层：所有可扩展组件（模型、工具、沙箱、防护）通过 `config.yaml` 字符串路径注入，`resolve_variable()` 动态加载
- `GuardrailProvider` 通过 `resolve_variable()` 注入，支持热插拔

```python
# 配置驱动注入示例
provider_cls = resolve_variable(guardrails_config.provider.use)
provider_kwargs = dict(guardrails_config.provider.config) if guardrails_config.provider.config else {}
provider = provider_cls(**provider_kwargs)
middlewares.append(GuardrailMiddleware(provider, ...))
```

## 三、行为型模式 (Behavioral Patterns)

### 3.1 责任链模式 (Chain of Responsibility)

**中间件链**是项目中最大规模的责任链实现。

18 层中间件构成处理管道，每层负责一个横切关注点：

```
ThreadData → Uploads → Sandbox → DanglingToolCall → LLMErrorHandling → 
Guardrail → SandboxAudit → ToolErrorHandling → Summarization → 
TodoList → TokenUsage → Title → Memory → ViewImage → 
DeferredToolFilter → SubagentLimit → LoopDetection → Clarification
```

中间件接口（`AgentMiddleware`）提供多个钩子方法：
- `before_model()` / `after_model()` — LLM 调用前后
- `before_tool()` / `after_tool()` — 工具调用前后
- `wrap_model_call()` / `wrap_tool_call()` — 完全包装调用（同步 + 异步）

每个中间件可以：
- **传递**请求到链中的下一个处理器
- **中断**链（如 `ClarificationMiddleware` 通过 `Command(goto=END)`）
- **修改**请求/响应（如 `ViewImageMiddleware` 注入 base64 图像数据）

### 3.2 策略模式 (Strategy)

运行时选择算法或行为：

| 策略 | 可选值 | 选择机制 |
|------|--------|---------|
| `multitask_strategy` | `reject` / `intercept` / `rollback` | 客户端请求参数 |
| 沙箱提供商 | `LocalSandboxProvider` / `AioSandboxProvider` | `config.yaml` `sandbox.use` |
| 模型提供商 | OpenAI / vLLM / 任意 LangChain 模型 | `config.yaml` `models[].use` |
| `on_disconnect` | `cancel` / `continue` | 客户端请求参数 |
| 流模式 | `values` / `messages-tuple` / `custom` | 客户端 `stream_mode` 参数 |

策略模式的核心优势在本项目中体现在：**通过配置而非继承扩展行为**。

### 3.3 观察者模式 (Observer)

事件驱动的一对多通知：

- **StreamBridge** — SSE 消费者 `subscribe()` 到 run 的事件流，生产者 `publish()` 时所有订阅者收到通知
- **MessageBus** (`app/channels/message_bus.py`) — IM 消息的异步发布-订阅中枢：`publish_inbound()` → 队列 → `_dispatch_loop()` 消费 → 回调分发
- **RunManager** — 通过 `abort_event`（`asyncio.Event`）实现取消信号的观察者模式

SSE 协议本身就是观察者模式在 HTTP 上的一种实现：服务端持续推送事件，客户端被动接收。

### 3.4 状态模式 (State)

通过有限状态机管理生命周期：

**RunRecord 状态机**：

```
pending → running → completed
                   → failed
                   → interrupted (通过 cancel / 新 run 的 interrupt 策略)
```

状态迁移由 `RunManager.set_status()` 封装，持久化到 `RunStore`。

**Sandbox 生命周期**：
```
acquire → (使用中) → release
```

由 `SandboxProvider` 统一管理，LocalSandboxProvider 使用 LRU 缓存（256 条目）+ `threading.Lock` 控制并发。

### 3.5 模板方法模式 (Template Method)

基类定义算法骨架，子类实现具体步骤：

- **类 `AgentMiddleware`** — 定义 `before_model / after_model / before_tool / after_tool / wrap_model_call / wrap_tool_call` 等钩子，所有 18 个中间件各自实现关心的钩子
- **类 `Channel`** (`app/channels/base.py`) — 定义 `start / stop / send / send_file / receive_file` 生命周期骨架，Slack/Feishu/Telegram/DingTalk 各自实现平台细节
- **类 `Sandbox`** — 定义 `execute_command / read_file / write_file / list_dir / glob / grep` 骨架，`LocalSandbox` 和 `AioSandbox` 各自实现

### 3.6 命令模式 (Command)

将请求或操作封装为对象：

- **`Command(goto=END)`** — LangGraph 的原语，将"中断执行"封装为命令对象，由 `ClarificationMiddleware` 在拦截 `ask_clarification` 工具调用时发出
- **`asyncio.Task.cancel()`** — Python 内置的命令模式，用于取消正在执行的 run
- **`abort_action`** (`interrupt` / `rollback`) — 封装取消的具体行为策略

## 四、架构模式 (Architectural Patterns)

### 4.1 分层架构 (Layered Architecture)

代码库严格分为两层，具有单方向依赖约束：

```
+------------------------------------------+
| App (app/)                               |
| FastAPI Gateway / IM Channels / Routes   |
+--------------------+---------------------+
                     | 依赖方向 ↓
+--------------------+---------------------+
| Harness (packages/harness/deerflow/)     |
| Agent / Tools / Sandbox / Models / MCP   |
+------------------------------------------+
```

**约束原则**：
- App 可以 import Harness
- Harness **禁止** import App（通过 CI 测试 `test_harness_boundary.py` 强制检查）
- 这是"依赖倒置原则"在包架构层面的实践

### 4.2 发布-订阅架构 (Pub-Sub)

两个核心的 Pub-Sub 实现：

1. **StreamBridge** — 每个 run 的事件流：
   - 生产者：`run_agent()` worker 发布 `metadata / updates / events / error / end` 
   - 消费者：SSE endpoint 在 HTTP 长连接上持续消费
   - 特性：`HEARTBEAT_SENTINEL`（15s 心跳）、`END_SENTINEL`（流终止）、`Last-Event-ID` 断线重连

2. **MessageBus** — IM 通道的消息路由：
   - `InboundMessage` → 队列 → 分发到 ChannelManager
   - `OutboundMessage` → 回调 → 各 Channel 实现发送回 IM 平台

### 4.3 提供者模式 (Provider)

项目中广泛使用的变体策略模式，强调生命周期管理：

```python
class SandboxProvider(ABC):
    def acquire(self, thread_id: str | None = None) -> str
    def acquire_async(self, thread_id: str | None = None) -> str
    def get(self, sandbox_id: str) -> Sandbox | None
    def release(self, sandbox_id: str) -> None
    def reset(self) -> None
```

提供者有明确的生命周期：acquire → get（使用中）→ release。类似模式用在：
- 模型提供商：通过 `config.yaml` `models[].use` 配置
- Guardrail 提供商：通过 `config.yaml` `guardrails.provider.use` 配置
- 沙箱提供商：通过 `config.yaml` `sandbox.use` 配置

### 4.4 仓储模式 (Repository)

数据访问抽象层，将存储实现与业务逻辑分离：

- `RunStore` — run 元数据的持久化（内存 / SQLite）
- `RunEventStore` — run 事件的持久化（内存 / SQLite）
- `FeedbackRepo` — 用户反馈的持久化
- `ThreadStore` — 线程元数据的持久化

每个仓储定义了清晰的接口，Gateway 通过依赖注入获取实现，存储后端可切换。

### 4.5 管道-过滤器 (Pipeline and Filter)

Agent 消息处理管道符合管道-过滤器架构：

```
用户输入 → ThreadState 初始化 → 中间件链(18层) → LLM 调用 → 工具执行 → 状态更新 → Checkpointer 持久化
```

每个中间件是一个**过滤器**，可以：
- 转换数据（`ViewImageMiddleware` 注入图像）
- 验证/过滤（`GuardrailMiddleware` 授权检查）
- 注入上下文（`ThreadDataMiddleware` 创建目录）
- 收集元数据（`TokenUsageMiddleware` 统计 tokens）
- 条件性短路（`LoopDetectionMiddleware` 检测循环后强制输出）

## 五、设计原则 (Design Principles)

### 5.1 SOLID 原则

| 原则 | 体现 |
|------|------|
| **单一职责** | 每个中间件只关注一个横切关注点（如 `SandboxMiddleware` 只管理沙箱生命周期、`MemoryMiddleware` 只处理记忆提取） |
| **开闭原则** | 新工具通过 `config.yaml` 配置即可加入，无需修改代码；新中间件只需实现 `AgentMiddleware` 接口并加入链 |
| **里氏替换** | `LocalSandbox` 和 `AioSandbox` 可互换使用，两者都遵循 `Sandbox` 接口；`Channel` 的各实现也遵循此原则 |
| **接口隔离** | `GuardrailProvider` 是 `Protocol` 而非庞大基类，只需实现 `evaluate` 和 `aevaluate`；委托给接口拥有者定义最小接口 |
| **依赖倒置** | 高层（Gateway）依赖抽象（`StreamBridge` / `RunStore`），而非具体实现；注入点集中管理 |

### 5.2 组合优于继承

- 中间件链通过**组合**多个 `AgentMiddleware` 实例构建，而非创建多层继承树
- `DeerFlowClient` 通过组合 `make_lead_agent`、`StreamBridge`、`RunManager` 实现功能
- `RunManager` 组合 `RunStore` 作为可选持久化后端
- Sandbox 工具通过组合 `Sandbox` 实例而非继承来扩展行为

### 5.3 配置驱动 (Convention over Configuration + Externalized Configuration)

核心设计决策：

```yaml
# config.yaml 驱动几乎所有扩展点
models:
  - use: "deerflow.models.vllm_provider:VllmChatModel"
    supports_thinking: true
sandbox:
  use: "deerflow.sandbox.local.local_sandbox_provider:LocalSandboxProvider"
guardrails:
  provider:
    use: "deerflow.guardrails.allowlist.AllowlistProvider"
```

- 工具、模型、沙箱、防护、MCP、技能都可以通过配置添加
- 环境变量引用（以 `$` 开头的值）支持敏感信息外部化
- `extensions_config.json` 管理 MCP 服务器和技能开关，API 可热更新

### 5.4 最小知识原则 (Law of Demeter)

- 中间件之间不直接交互，只通过 `ThreadState` 共享状态
- `SubagentExecutor` 不关心子代理内部实现，只通过 `SubagentResult` 接收结果
- `StreamBridge` 的消费者和生产者在不同协程中运行，互不了解

### 5.5 好莱坞原则 ("Don't call us, we'll call you")

- **中间件框架**：中间件不主动执行，而是由 LangGraph 运行时在合适的时机调用其钩子方法
- **Channel 生命周期**：`ChannelManager` 控制 `start / stop`，Channel 实现只响应这些调用
- **`get_app_config()` 回调**：自动监听文件 mtime 变化，调用方无需手动刷新

### 5.6 关注点分离 (Separation of Concerns)

**三层分离**：

```
HTTP 层 (Gateway routes)    → 请求解析、鉴权、序列化
服务层 (services + run_agent) → 业务逻辑：创建 run、组装 config、流处理
基础设施层 (tools/sandbox/models) → 具体能力实现
```

Gateway 路由不直接操作 runtime，通过 `services.py` 中转。`thread_runs.py` 中的端点平均不到 20 行，业务逻辑在 `services.py` 和 `run_agent()`（`worker.py`）中。

### 5.7 防御性编程

- **SQLite 重试** (`_call_store_with_retry`) — 针对 `SQLITE_BUSY / SQLITE_LOCKED` 的指数退避重试（最多 5 次）
- **边界检查** (`test_harness_boundary.py`) — CI 中强制验证 harness 不反向依赖 app
- **File I/O 原子性** — Memory 写入使用临时文件 + rename 替代直接覆写
- **死信安全** (`sandbox.py`) — `write_file` 确保目录存在再写入；`str_replace` 用文件锁防止并发冲突
- **HTTP 输入验证** (`services.py normalize_input`) — 非法消息结构返回 400 而非 500

## 六、并发与异步模式

### 6.1 异步生产者-消费者

```
run_agent()  →  StreamBridge.publish()  →  SSE subscriber
(生产者)           (异步队列/通道)           (消费者)
```

使用 `asyncio` 原语而非外部消息队列，适合单进程内生产消费解耦。

### 6.2 后台任务 + 事件通知

`RunManager` 使用 `asyncio.create_task()` 启动后台 agent 执行，结合 `asyncio.Event`（`abort_event`）实现可控取消：

```python
record.task = asyncio.create_task(run_agent(...))
# 取消时：
record.abort_event.set()
record.task.cancel()
```

### 6.3 线程池隔离

子代理使用双线程池隔离：
- `_scheduler_pool`（3 个 worker）— 调度
- `_execution_pool`（3 个 worker）— 执行
- 避免子代理占用主 event loop，同时限制并发度

### 6.4 LRU 缓存 + 锁

`LocalSandboxProvider` 使用 `threading.Lock` + LRU 缓存（256 条目）管理每个 thread 的沙箱实例，在并发访问和资源释放之间取得平衡。

## 七、领域驱动设计概念

### 7.1 有界上下文 (Bounded Context)

代码库通过包结构清晰界定上下文边界：

| 上下文 | 包路径 | 职责 |
|--------|--------|------|
| Agent 执行 | `agents/` | LangGraph 图、中间件链、状态管理 |
| 沙箱隔离 | `sandbox/` | 安全执行环境、文件系统虚拟化 |
| 子代理 | `subagents/` | 任务分解、并行执行 |
| 模型管理 | `models/` | LLM 工厂、thinking/vision 支持 |
| MCP 集成 | `mcp/` | 外部工具服务器管理 |
| 技能系统 | `skills/` | 技能发现和加载 |
| 记忆系统 | `agents/memory/` | 持久化记忆提取和注入 |
| IM 通道 | `app/channels/` | 多平台 IM 消息收发 |
| 运行时 | `runtime/` | Run 生命周期、StreamBridge、Checkpointer |

### 7.2 端口-适配器 (Ports and Adapters / Hexagonal Architecture)

项目将"端口"（接口）和"适配器"（实现）清晰分离：

| 端口 (Port) | 适配器 (Adapter) |
|------------|-----------------|
| `Sandbox` 接口 | `LocalSandbox` / `AioSandbox` |
| `SandboxProvider` | `LocalSandboxProvider` / `AioSandboxProvider` |
| `Channel` 基类 | Slack / Feishu / Telegram / DingTalk 实现 |
| `GuardrailProvider` Protocol | `AllowlistProvider` / 自定义提供者 |
| `RunStore` | 内存 / SQLite 实现 |
| `StreamBridge` | 具体实现 |

## 八、总结

### 模式密度分析

DeerFlow 的核心复杂度集中在**行为型模式**（特别是责任链和策略模式），这是由 AI Agent 框架的本质决定的：

1. **Agent 执行 = 层层过滤的管道** → 责任链模式（中间件）
2. **Agent 的决策点需要灵活切换** → 策略模式（沙箱、模型、multitask）
3. **Agent 需要感知和响应外部事件** → 观察者模式（SSE、MessageBus）
4. **Agent 配置需要热插拔** → 工厂模式 + 依赖注入

### 模式选择权衡

- **中间件链 vs 事件系统**：选择同步的责任链而非异步事件总线，因为每个中间件都依赖上一个的执行结果（顺序执行语义）
- **Provider 模式 vs 简单配置**：选择有生命周期的 Provider 而非静态配置，因为沙箱等资源需要 acquire/release 管理
- **组合 vs 继承**：18 个中间件通过组合而非多层继承实现，避免了"中间件爆炸"问题
- **抽象基类 vs Protocol**：既有传统 ABC（`Sandbox`、`Channel`），也有鸭子类型 Protocol（`GuardrailProvider`），根据是否需要共享状态选择
