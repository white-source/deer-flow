Q10 — 工作流编排的使用场景 

要理解什么时候需要工作流编排，先要看清楚现有机制（task 工具）能做什么、不能做什么。

 现有 task 工具的定位：并行子代理 

当前的  task  工具（见 task_tool.py:186-192）是给 LLM 做并行子任务分发的：

 ▎ "帮我查一下 X，搜一下 Y，再分析一下 Z" → 三个  task  调用并发执行，结果一起回来。

它的天然约束：

 · 各子任务互相独立（不依赖彼此输出）
 · 所有子任务用同一个模型配置（当前 thread 的 model）
 · 输出全部回到 lead agent → 由 lead agent 手动合成

 工作流编排 vs 现有 task 工具 

 task 工具（当前）：                  工作流编排（Q10 新增）： 
  
 ┌─ Lead Agent ─┐                   ┌─ Workflow Engine ─────────┐ 
 │  "查A" → task│                   │ Step 1 [模型A]: 抓取数据  │ 
 │  "查B" → task│  ← 并行独立        │        ↓                  │ 
 │  "查C" → task│                   │ Step 2 [模型B]: 清洗数据  │  ← 顺序管道 
 │              │                   │        ↓                  │ 
 │  合成结果    │                   │ Step 3 [模型C]: 生成报告  │ 
 └──────────────┘                   └───────────────────────────┘ 

 典型使用场景 

 场景 1：数据 ETL 管道 

 用户："每天自动从公司 API 拉取销售数据，清洗后写入 BI 数据库" 
  
 工作流步骤： 
   Step 1 [gpt-4o]     →  连接 API、鉴权、下载原始 JSON 
   Step 2 [gpt-4o-mini] →  清洗、去重、格式转换（便宜模型就够了） 
   Step 3 [自定义模型]   →  写入 ClickHouse / MySQL 

关键点：每步需要不同模型（便宜模型做清洗，贵模型做复杂逻辑），且上一步失败就不执行下一步。

 场景 2：多步代码审查流水线 

 工作流步骤： 
   Step 1 [claude-opus]   →  审查代码正确性 
   Step 2 [gpt-4o-mini]   →  检查代码风格/注释（便宜模型够用） 
   Step 3 [deepseek]      →  生成测试用例 

现有  task  做不到的原因是：Step 2 需要 Step 1 的输出作为输入，且各步骤意愿用不同模型。

 场景 3：用户定义的自动化 SOP 

 用户："每次有新客户询盘，先查 CRM 看是否老客户， 
        如果不是，搜索公司背景，然后生成报价邮件草稿" 
  
 工作流步骤： 
   Step 1 [模型A] →  CRM 查询（用 fast 模型快速查） 
   Step 2 [模型B] →  如新客户，搜索公司官网/LinkedIn 
   Step 3 [模型C] →  根据前两步结果生成报价邮件 

这里的条件分支（Step 2 取决于 Step 1 的结果）是现有  task  根本做不到的。

 场景 4：需要不同 Agent Config 的步骤 

 工作流步骤： 
   Step 1 [default agent, tool_groups: ["database"]] 
     → 连接数据库，查询原始数据 
   Step 2 [default agent, tool_groups: ["sandbox"]] 
     → 在沙箱中运行 Python 脚本做数据分析 
   Step 3 [custom agent "writer", 无 sandbox] 
     → 根据分析结果生成 Markdown 报告 

不同的步骤需要不同的工具集合和 agent config（SOUL.md），甚至某个步骤要用一个完全自定义的 agent。

 场景 5：带中断/审批的工作流 

 工作流步骤： 
   Step 1 → 生成设计稿 
   Step 2 ⏸️ 等待用户审批（中断 -> resume） 
   Step 3 → 如果批准，部署上线；否则回到 Step 1 

LangGraph 原生支持  interrupt ，但现有  task  工具不支持跨步骤中断等待。工作流编排可以在步骤之间插入  Command(goto=...)  /  interrupt_before  实现人工审批。

 一句话总结 

 场景                                         现有 task 工具 工作流编排（Q10）     
 ──────────────────────────────────────────── ────────────── ──────────────────────
 "同时查 A、B、C 三个不相关的事"              ✅ 完美        ❌ 过重               
 "先 X 再 Y 再 Z，上一步的输出是下一步的输入" ❌ 不行        ✅ 设计目标           
 "不同步骤用不同模型/不同工具集"              ❌ 不行        ✅ 设计目标           
 "步骤之间有 if/else 条件分支"                ❌ 不行        ✅ 可支持             
 "步骤执行到一半等人批准"                     ❌ 不行        ✅ 可支持（interrupt）
 "步骤失败时不需要重试整个流程"               ❌ 全部重来    ✅ 从失败步骤恢复     

工作流编排不是为了替代  task  工具，而是补上"顺序管道 + 多模型 + 条件分支 + 人工审批"这块空白。 简单的并行子任务仍然应该用  task 。
