# DeerFlow 核心主流程链路

> 梳理框架中几条核心请求/执行路径，理解数据如何穿越各层。

---

## 一、用户消息处理主链路

最核心的链路：用户通过 HTTP 发送消息 → Agent 推理 → 流式返回结果。

```
┌──────────────────────────────────────────────────────────────────┐
│  Frontend (Next.js) / curl                                       │
│  POST /api/threads/{id}/runs/stream                              │
└──────────────────────────┬───────────────────────────────────────┘
                           │ HTTP Request
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│  Gateway Router: thread_runs.py                                  │
│  stream_run() → start_run()                                      │
│  1. 验证请求 body (RunCreateRequest Pydantic)                     │
│  2. 解析 multitask_strategy / on_disconnect / stream_mode        │
│  3. 验证 model_name (在配置允许列表中)                              │
└──────────────────────────┬───────────────────────────────────────┘
                           │ await run_mgr.create_or_reject()
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│  RunManager.create_or_reject()                                   │
│  1. 检查 thread 是否有 inflight run                                │
│     - reject 策略: 有则抛 ConflictError → HTTP 409                │
│     - interrupt/rollback 策略: 取消现有 run                        │
│  2. 创建新 RunRecord (status=pending)                             │
│  3. 持久化到 RunStore (SQLite)                                    │
└──────────────────────────┬───────────────────────────────────────┘
                           │ return record
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│  start_run() (继续)                                              │
│  1. upsert thread_meta                                           │
│  2. resolve_agent_factory → make_lead_agent                      │
│  3. normalize_input → 消息格式规范化                                │
│  4. build_run_config → 合并 thread_id, context, metadata          │
│  5. merge_run_context_overrides → 注入 model_name等               │
│  6. asyncio.create_task(run_agent(...))                          │
└──────────────────────────┬───────────────────────────────────────┘
                           │ 后台 asyncio Task
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│  run_agent() (worker.py)                                         │
│  1. run_manager.set_status(running)                              │
│  2. 快照 pre-run checkpoint (用于 rollback)                       │
│  3. bridge.publish("metadata", {run_id, thread_id})              │
│  4. 构造 Runtime(context, store)                                  │
│  5. 注入 RunJournal (token 统计 + 事件记录)                        │
│  6. agent_factory(config) → 创建 LangGraph agent                 │
│  7. 挂载 checkpointer + store                                     │
│  8. agent.astream(graph_input, stream_mode=[...])                │
│     → 每个 chunk 通过 bridge.publish() 发布                        │
│  9. 完成后 set_status(success/failed/interrupted)                │
│  10. finally: 同步 title、更新 thread_meta、publish_end()          │
└──────────────────────────┬───────────────────────────────────────┘
                           │ SSE 事件流
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│  sse_consumer() (services.py)                                    │
│  bridge.subscribe(run_id) 消费事件                                │
│  1. HEARTBEAT_SENTINEL → ": heartbeat\n\n" (保活)                │
│  2. StreamEvent(event, data) → "event: {event}\ndata: {json}\n"  │
│  3. END_SENTINEL → "event: end\n" → 关闭连接                      │
│  4. on_disconnect=cancel 且客户端断连 → cancel run                │
└──────────────────────────┬───────────────────────────────────────┘
                           │ HTTP Streaming Response
                           ▼
┌──────────────────────────────────────────────────────────────────┐
│  Frontend                                                        │
│  useStream React hook 消费 SSE:                                  │
│  - "metadata" → 获取 run_id, thread_id                           │
│  - "values" → 更新完整状态快照                                     │
│  - "messages" → 逐 chunk 拼接消息内容                              │
│  - "end" → 流结束，展示完整响应                                    │
└──────────────────────────────────────────────────────────────────┘
```

### 关键设计点

- **双通道分离**：`start_run` 通过 `asyncio.create_task()` 在后台执行 agent，`sse_consumer` 独立订阅 StreamBridge 消费事件。生产和消费在不同协程中并行。
- **StreamBridge 解耦**：agent worker 不知道 HTTP 的存在，只调用 `bridge.publish()`；SSE endpoint 不知道 agent 内部细节，只调用 `bridge.subscribe()`。
- **断连处理**：HTTP 层通过 `request.is_disconnected()` 检测客户端断开，根据 `on_disconnect` 策略决定是取消 run 还是继续执行。

## 二、Agent 构建链路

创建 LangGraph agent 的全过程。

```
start_run()
  └─ resolve_agent_factory(assistant_id)
       └─ make_lead_agent(config, app_config)           ← langgraph.json 注册
            │
            ├─ _resolve_model_name(config)               → 确定 LLM 模型
            ├─ create_chat_model(name, thinking_enabled) → 实例化 LLM
            │
            ├─ get_available_tools(...)                   → 组装工具列表
            │   ├─ 配置工具 (config.yaml tools[])
            │   ├─ MCP 工具 (mcp.get_cached_mcp_tools())
            │   ├─ 内置工具 (present_files, ask_clarification, view_image)
            │   └─ 子代理工具 (task, 如果 subagent_enabled)
            │
            ├─ apply_prompt_template(config)              → 组装系统提示词
            │   ├─ 基础系统提示 (SYSTEM_PROMPT_TEMPLATE)
            │   ├─ 子代理指令 (<subagent_system>)
            │   ├─ 技能参考 (<skill_system>)
            │   ├─ 记忆注入 (<memory> tags)
            │   ├─ 延期工具提示 (get_deferred_tools_prompt_section)
            │   └─ (可选) 引导模式 / 技能演化等
            │
            ├─ _build_middlewares(config, ...)            → 组装 18 层中间件
            │   └─ [参见中间件执行链路章节]
            │
            └─ create_agent(model, tools, ..., middlewares=middlewares)
                 → LangGraph StateGraph (model_node → tool_node)
```

### 关键设计点

- `create_agent()` 创建二节点图：**model node**（LLM 调用）和 **tool node**（工具执行），两者循环直到 LLM 输出非工具消息。
- `apply_prompt_template()` 在 `prompt.py:768` 动态组装系统提示词，每种内容（子代理、技能、记忆等）都是独立的构建函数。
- `get_available_tools()` 根据 `groups`、`model_name`、`subagent_enabled` 等条件动态过滤。

## 三、中间件执行链路

18 层中间件的执行顺序和职责。每次 LLM 调用和每次工具调用都会经过相应钩子。

```
┌─────────────────────────────────────────────────────────────────┐
│                   中间件链 (执行顺序 ↓)                           │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. ThreadDataMiddleware                                        │
│     before_agent: 创建 per-thread 工作目录                       │
│     (user-data/{workspace,uploads,outputs})                     │
│                                                                 │
│  2. UploadsMiddleware  (仅 lead agent)                          │
│     before_model: 注入新上传的文件列表到对话                      │
│                                                                 │
│  3. SandboxMiddleware                                           │
│     before_tool(首次): acquire sandbox (lazy_init)              │
│     sandbox_id 存入 state                                       │
│                                                                 │
│  4. DanglingToolCallMiddleware                                  │
│     after_model: 为残留 tool_calls 注入占位 ToolMessage         │
│     (因中断导致 LLM 有 tool_call 但无对应结果)                   │
│                                                                 │
│  5. LLMErrorHandlingMiddleware                                  │
│     wrap_model_call: 捕获 LLM 异常 → 错误 ToolMessage           │
│                                                                 │
│  6. GuardrailMiddleware (可选)                                  │
│     before_tool: 评估工具调用授权                                │
│     (GuardrailProvider.evaluate())                              │
│                                                                 │
│  7. SandboxAuditMiddleware                                      │
│     before_tool: 记录沙箱命令审计日志                            │
│                                                                 │
│  8. ToolErrorHandlingMiddleware                                 │
│     wrap_tool_call: 捕获工具异常 → 错误 ToolMessage              │
│                                                                 │
│  ─────────────────────────────────────────────────────────      │
│  以下在 agent.py 中追加 (lead-agent 专属)                        │
│  ─────────────────────────────────────────────────────────      │
│                                                                 │
│  9. SummarizationMiddleware (可选)                              │
│     after_agent: token 接近限制时自动摘要历史                    │
│                                                                 │
│ 10. TodoListMiddleware (可选, plan_mode)                        │
│     提供 write_todos 工具，跟踪任务进度                          │
│                                                                 │
│ 11. TokenUsageMiddleware (可选)                                 │
│     after_model: 累计 token 用量                                │
│                                                                 │
│ 12. TitleMiddleware                                             │
│     after_agent: 首次完整对话后自动生成线程标题                  │
│                                                                 │
│ 13. MemoryMiddleware                                            │
│     after_agent: 过滤消息 → 入队记忆提取队列                    │
│                                                                 │
│ 14. ViewImageMiddleware (条件, vision 模型)                     │
│     before_model: 注入 base64 图像数据                          │
│                                                                 │
│ 15. DeferredToolFilterMiddleware (可选)                         │
│     before_model: 隐藏延期工具模式                               │
│                                                                 │
│ 16. SubagentLimitMiddleware (条件, subagent_enabled)            │
│     after_model: 截断多余 task 调用 (最多 3 个)                  │
│                                                                 │
│ 17. LoopDetectionMiddleware                                     │
│     after_model: 检测重复工具调用循环 → 强制文本回答             │
│                                                                 │
│ 18. ClarificationMiddleware                                     │
│     before_tool: 拦截 ask_clarification → Command(goto=END)     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

### 中间件构建位置

- `tool_error_handling_middleware.py:_build_runtime_middlewares()` → 1~8 号（基础，lead/subagent 共享）
- `agent.py:_build_middlewares()` → 9~18 号（lead-agent 专属）

### 关键设计点

- **分层组装**：基础中间件在 runtime 层共享，lead-agent 专属中间件在 agent 层追加。
- **责任链模式**：每个中间件只关注一个横切关注点，通过组合而非继承实现 18 层链。
- **中断机制**：`ClarificationMiddleware` 通过 LangGraph 的 `Command(goto=END)` 原语中断执行流。

## 四、子代理执行链路

Agent 调用 `task` 工具 → 子代理在后台执行 → 收集结果。

```
┌──────────────────────────────────────────────────────────┐
│  Lead Agent                                              │
│  LLM 决定拆分任务 → 调用 task(prompt=...) 工具           │
│  一次可发出多个 task 调用 (批量分解)                      │
└─────────────────────┬────────────────────────────────────┘
                      │ SubagentLimitMiddleware 截断超过 3 个
                      ▼
┌──────────────────────────────────────────────────────────┐
│  SubagentExecutor.execute(task)                          │
│                                                          │
│  1. 检测当前事件循环                                      │
│     - 有运行中 loop → _execute_in_isolated_loop()        │
│     - 无运行中 loop → asyncio.run()                      │
│                                                          │
│  2. _scheduler_pool.submit() → 调度线程池 (3 worker)    │
│  3. _execution_pool.submit() → 执行线程池 (3 worker)    │
│                                                          │
│  4. 构建子代理:                                          │
│     - 确定 subagent_type (general-purpose / bash)        │
│     - 动态加载子代理工具 (config.yaml subagents[])       │
│     - 过滤工具 (Skill allowed-tools 策略)                │
│     - 创建子代理 LLM + 工具 + 提示词                     │
│                                                          │
│  5. 执行子代理:                                          │
│     langchain.create_agent() → agent.invoke()            │
│                                                          │
│  6. 每 5 秒轮询 → SSE 推送事件:                           │
│     task_started → task_running → task_completed         │
│                                    task_failed           │
│                                    task_timed_out(15min) │
│                                                          │
│  7. 返回 SubagentResult {status, result/error}           │
└─────────────────────┬────────────────────────────────────┘
                      │ 结果返回 lead agent
                      ▼
┌──────────────────────────────────────────────────────────┐
│  Lead Agent 继续执行                                      │
│  LLM 收到 task 结果，整合到最终回复                        │
└──────────────────────────────────────────────────────────┘
```

### 关键设计点

- **双线程池隔离**：调度和执行分离，避免阻塞主 event loop。
- **隔离事件循环**：从已有事件循环调用时，使用独立事件循环避免冲突。
- **批量执行**：LLM 一次最多发出 3 个 `task` 调用，并行执行后汇总。

## 五、SSE 流式响应链路

从 `run_agent` 产生事件 → StreamBridge → HTTP 客户端。

```
┌────────────────────────────────────────────────────────────┐
│  run_agent() (worker.py)                                    │
│                                                             │
│  agent.astream(graph_input, stream_mode=["values",          │
│    "messages", "custom"])                                    │
│                                                             │
│  ↳ values 模式 → serialize(chunk) → bridge.publish()       │
│  ↳ messages 模式 → (chunk, metadata) → bridge.publish()    │
│                                                             │
│  publish_end(run_id) → 通知流结束                            │
│  cleanup: asyncio.create_task(bridge.cleanup(run_id, 60))   │
└───────────────────────────┬─────────────────────────────────┘
                            │ bridge.publish()
                            ▼
┌────────────────────────────────────────────────────────────┐
│  InMemoryStreamBridge                                       │
│                                                             │
│  publish(run_id, event, data):                              │
│    1. 生成递增 event_id                                     │
│    2. 创建 StreamEvent(id, event, data)                     │
│    3. 放入 run_id 对应的 asyncio.Queue                      │
│                                                             │
│  subscribe(run_id, last_event_id, heartbeat_interval):      │
│    while not end:                                            │
│      try: queue.get(timeout=heartbeat_interval)             │
│      except: yield HEARTBEAT_SENTINEL                       │
│      if END_SENTINEL: break                                 │
│      if event_id > last_event_id: yield event               │
└───────────────────────────┬─────────────────────────────────┘
                            │ async for entry in bridge.subscribe()
                            ▼
┌────────────────────────────────────────────────────────────┐
│  sse_consumer() (services.py)                               │
│                                                             │
│  StreamingResponse:                                          │
│  async for entry in bridge.subscribe(run_id):               │
│    if 客户端断连: break                                      │
│    if HEARTBEAT_SENTINEL: yield ": heartbeat\n\n"           │
│    if END_SENTINEL: yield "event: end\n..." → return        │
│    else: yield f"event: {entry.event}\ndata: {json}\n..."   │
│                                                             │
│  finally: if on_disconnect=cancel: run_mgr.cancel(run_id)  │
└────────────────────────────────────────────────────────────┘
```

### SSE 协议格式

```
event: metadata
data: {"run_id":"...","thread_id":"..."}

event: messages
data: {"content":"Hello"}

: heartbeat              ← 15 秒无事件时发送

event: end
data: null
```

### 关键设计点

- **Last-Event-ID 重连**：支持断线重连，客户端发送上次收到的事件 ID。
- **15 秒心跳**：防止代理/负载均衡断开长连接。
- **延迟清理**：`cleanup(delay=60)` 给晚连接的订阅者留出时间。

## 六、IM 通道消息链路

外部 IM 消息 → Channel → MessageBus → ChannelManager → Gateway → Agent → 回复。

```
┌──────────────┐
│  用户发消息   │
│  (飞书/Slack  │
│  /Telegram等)│
└──────┬───────┘
       │ HTTP Webhook / WebSocket
       ▼
┌──────────────────────────────────────────────────────────────┐
│  IM Channel 实现 (feishu.py / slack.py / telegram.py 等)      │
│  1. 解析平台回调 → 消息内容、用户 ID、聊天 ID                    │
│  2. 创建 InboundMessage                                       │
│  3. message_bus.publish_inbound(msg)                          │
└──────────────────────────┬───────────────────────────────────┘
                           │ asyncio.Queue
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  ChannelManager._dispatch_loop()                              │
│  持续消费 message_bus.get_inbound()                           │
│                                                               │
│  1. 映射 chat_id → thread_id (store.py 持久化)                │
│  2. 命令 (/new, /status 等) → 直接处理                        │
│  3. 普通消息 → 通过 langgraph-sdk HTTP 调用 Gateway           │
│                                                               │
│  飞书: runs.stream() → 持续更新消息卡片                        │
│  Slack/Telegram: runs.wait() → 一次性发送回复                 │
│                                                               │
│  4. message_bus.publish_outbound(outbound)                    │
└──────────────────────────┬───────────────────────────────────┘
                           ▼
┌──────────────────────────────────────────────────────────────┐
│  Channel.send(outbound)                                       │
│  飞书: 发送/更新卡片 (patch)                                   │
│  Slack: 发送消息到 channel                                    │
│  Telegram: 发送消息到 chat                                    │
│  DingTalk: AI Card 流式更新或 sampleMarkdown                  │
└──────────────────────────────────────────────────────────────┘
```

### 关键设计点

- **chat_id → thread_id 映射**：JSON 文件持久化，同一 IM 对话映射到同一 DeerFlow 线程。
- **流式 vs 阻塞**：飞书用 `runs.stream()` 逐步更新卡片；Slack/Telegram 用 `runs.wait()` 一次性回复。
- **消息总线**：`MessageBus` 通过 `asyncio.Queue` 解耦 Channel 实现和消息分发。

## 七、取消/中断链路

用户取消正在执行的 run 的完整路径。

```
┌──────────────────────────────────────────────────────┐
│  POST /api/threads/{id}/runs/{rid}/cancel            │
│  ?action=interrupt|rollback&wait=true|false          │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│  RunManager.cancel(run_id, action)                   │
│  1. 检查 run 状态 (pending 或 running)               │
│  2. record.abort_action = action                     │
│  3. record.abort_event.set()  ← asyncio.Event       │
│  4. if task and not done: task.cancel()              │
│  5. status = RunStatus.interrupted                   │
│  6. 持久化到 RunStore                                │
└──────────────────────┬───────────────────────────────┘
                       │ 两个路径:
                       ▼
┌─────────────────────────────┐  ┌─────────────────────────────┐
│  asyncio.Task.cancel() 路径  │  │  abort_event 检测路径        │
│                             │  │                             │
│  run_agent 收到 Cancelled-  │  │  astream 循环中:            │
│  Error → except 分支        │  │  if abort_event.is_set():  │
│                             │  │      break                  │
│  if rollback:               │  │                             │
│    恢复 checkpoint           │  │  然后: set_status +         │
│  else: set_status(interrupt)│  │  publish_end + cleanup()    │
└─────────────────────────────┘  └─────────────────────────────┘
```

### 两种取消策略

| 策略 | `interrupt` | `rollback` |
|------|-------------|------------|
| 当前 run 状态 | `interrupted` | `error` |
| Thread 状态 | 保留 run 中消息 | 回到 run 之前的状态 |
| 后续对话 | 历史保留 | 像没发生过 |

## 八、记忆系统链路

对话 → 提取 → 存储 → 注入的完整周期。

```
┌──────────────────────────────────────────────────────────────┐
│  1. MemoryMiddleware.after_agent()                           │
│     过滤: 只保留 user 消息 + 最终 AI 回复                     │
│     捕获: get_effective_user_id() → user_id                  │
│     入队: queue.enqueue(thread_id, messages, user_id)        │
│     (同 thread 的未处理消息合并)                               │
│                                                               │
│  2. 等待 debounce_seconds (默认 30s)                         │
│                                                               │
│  3. MemoryUpdater.update(messages):                           │
│     → LLM 提取事实 + 更新上下文                                │
│     → 事实去重 (whitespace-normalized content)                │
│     → 原子写入 (temp file + rename)                          │
│     → 缓存失效                                               │
│                                                               │
│    存储 memory.json:                                          │
│    { userContext: {workContext, personalContext, topOfMind},  │
│      history: {recentMonths, earlierContext, longTermBg},     │
│      facts: [{id, content, category, confidence, ...}] }     │
└──────────────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────────────┐
│  4. 下次对话注入                                               │
│     apply_prompt_template()                                   │
│     → _get_memory_context(user_id, agent_name)                │
│     → 格式: <memory>...用户上下文、历史、最多15条事实...</memory> │
│     → 通过 DynamicContextMiddleware 放在第一个 HumanMessage    │
│       前的 <system-reminder> 中                                │
└──────────────────────────────────────────────────────────────┘
```

### 关键设计点

- **延迟处理**：30 秒 debounce 合并同一 thread 多次对话，减少 LLM 调用。
- **每用户隔离**：`{base_dir}/users/{user_id}/memory.json`。
- **注入位置**：不在 system prompt 中（前缀缓存复用），而是作为 `<system-reminder>` 在第一条 HumanMessage 前。
