这是当前 Agent 产品设计中的一个核心问题：**Agent 是一次性任务（Task）还是持续会话（Conversation）？**

你观察到的现象是对的：

> 大部分 Agent 在开始执行后，用户无法继续发送消息，或者发送了也不会影响当前任务。

原因在于绝大多数 Agent 框架本质上采用的是：

```text
用户输入
   ↓
生成执行计划
   ↓
开始执行
   ↓
执行完成
```

执行期间，任务状态已经固定。

---

# 为什么不能随便更新消息

假设用户说：

```text
帮我分析吉利汽车
```

Agent 已经开始：

```text
1. 搜索财报
2. 搜索行业数据
3. 分析估值
4. 生成报告
```

运行到第3步时，用户又发：

```text
只分析新能源业务
```

这时候出现问题：

### 问题1：执行计划已经生成

原计划：

```text
分析全部业务
```

新需求：

```text
只分析新能源
```

实际上：

```text
Task Definition 已变化
```

Agent 不知道：

```text
继续？
重规划？
终止？
```

---

### 问题2：上下文污染

Agent已经搜到了：

```text
燃油车数据
商用车数据
出口数据
```

但新任务只需要：

```text
新能源
```

之前执行结果是否保留？

这是个非常复杂的问题。

# Agent 的三种模式

## 模式1：Batch Mode（目前主流）

类似：

```text
Claude Code
Cursor Agent
OpenAI Deep Research
```

流程：

```text
User
 ↓
Prompt
 ↓
Plan
 ↓
Execute
 ↓
Finish
```

执行过程中：

```text
不能插话
```

或者：

```text
插话 = Stop + Restart
```

这是目前最稳定的模式。

---

## 模式2：Interrupt Mode

类似：

```text
人类做事情
```

Agent运行：

```text
正在分析吉利汽车...
```

用户：

```text
暂停
```

Agent：

```text
收到
保存状态
```

用户：

```text
改成分析比亚迪
```

Agent：

```text
重新规划
```

流程：

```text
Task
 ↓
Interrupt
 ↓
Replan
 ↓
Continue
```

这种已经比大多数 Agent 先进。

---

## 模式3：Streaming Collaboration（未来方向）

真正高级的 Agent 会变成：

```text
Agent ↔ User
持续协作
```

例如：

```text
Agent:
发现吉利有三块业务：
1. 新能源
2. 出口
3. 智驾

先分析哪个？
```

用户：

```text
新能源
```

Agent：

```text
好的
开始分析
```

分析中：

```text
发现极氪占比很高
是否展开？
```

用户：

```text
展开
```

这已经不是：

```text
Task
```

而是：

```text
Co-pilot
```

模式。

# 从架构角度看，需要什么能力

如果想支持运行过程中接收新消息，需要Agent具备：

### 1. Task State

任务状态机

```text
CREATED
PLANNING
RUNNING
PAUSED
REPLANNING
COMPLETED
```

---

### 2. Checkpoint

执行检查点

例如：

```text
Step1 完成
Step2 完成
Step3 进行中
```

用户修改需求：

```text
从最近Checkpoint恢复
```

而不是：

```text
全部重跑
```

---

### 3. Dynamic Planning

动态规划

不是：

```text
一次生成Plan
```

而是：

```text
执行一步
↓
重新思考
↓
执行下一步
```

很多论文称为：

```text
Plan-and-Execute
```

或

```text
ReAct
```

进一步演化为：

```text
Reflection Agent
Adaptive Agent
```

---

### 4. Event Bus

消息总线

Agent运行时持续监听：

```text
User Message
System Event
Tool Result
Timeout
```

类似：

```text
Kafka
RabbitMQ
Actor Model
```

的思想。

# 为什么 Claude Code 体验比较接近

例如在 Claude Code 中：

```text
分析这个项目
```

运行过程中你可以：


# 如果你自己设计 Agent

对于 Agent 产品设计，我会建议采用：

```text
Conversation
   ↓
Task
      ↓
Plan
      ↓
Step
```

结构：

```text
Conversation
 ├─ User Message
 ├─ User Message
 └─ User Message

Task
 ├─ Task V1
 ├─ Task V2
 └─ Task V3

Plan
 ├─ Step1
 ├─ Step2
 └─ Step3
```

用户新增消息时：

```text
生成 Task V2
```

而不是：

```text
直接修改正在运行的 Task V1
```

这样架构会清晰很多。

很多人认为 Agent 的未来是“更长的自动执行”。实际上更重要的能力可能是：

> **在长时间执行过程中，能够随时接收用户反馈、重新规划并继续执行。**

这比单纯把任务跑 30 分钟、1 小时更接近真实的人机协作模式。

发送了两条消息，看起来是排队完成的，请确认是串行完成的吗，支持同事并发跑吗，如果不支持需要做哪些改动；

查看当前队列与 Worker 的并发模型实现。

结论：你看到的两条消息是「同一会话内串行完成」，不是同时并发跑。

1. 同一会话（同一 thread_id）：串行
当前 enqueue 实现里，同一个 thread 同一时刻只跑一个 Run，后面的消息进 FIFO 队列，等前一个结束再启动。

依据：

RunDispatcher 文档与逻辑（dispatcher.py）：


dispatcher.py
Lines 38-39
class RunDispatcher:
    """Schedules runs with global concurrency limits and per-thread serialization."""
_active_threads：每个 thread_id 只允许一个 active run
on_run_finished → _drain_thread：前一个 run 结束后才 dequeue 并启动下一个
有专门测试 test_dispatcher_runs_queued_runs_serially_per_thread，断言第二个 run 必须等第一个完成才 launch
队列（queue.py）：per-thread FIFO，dequeue 从左取，保证顺序。

前端表现：

第一条：走 thread.submit，有 SSE 流式回复
第二条（第一条还在跑）：走 submitEnqueuedRun，返回 202 queued，上方显示 “N messages queued”
第二条真正执行要等第一条 run 结束，不会两条同时流式输出
所以你观察到的「排队完成」= 串行排队执行，符合设计。

2. 跨会话：可以并发
全局 Worker 池默认 4 个并发槽（deps.py 里 workers=4，config.example.yaml 也有 runs.workers: 4）：

不同 thread（不同聊天窗口 / 不同 thread_id）可以同时各跑一个 run
上限是全局 semaphore（默认 4），不是「每个 thread 一个 worker」
3. 单条消息内部的并行（已有）
同一会话串行，但 一条消息里 Lead Agent 仍可通过 task 工具派子代理，子代理在线程池里并行（见 docs/notes/多任务并行.md 方案 3）。这是「一次提问、内部多任务并行」，不是「用户连发两条消息同时跑」。

4. 若要做「同一会话多条消息同时跑」：目前不支持，需 Phase 3 级改动
计划文档里把这叫 Phase 3（同线程真并行），MVP 刻意不做，原因是 同一 thread_id 共享一条 LangGraph checkpoint 链，多 run 同时写会冲突。

子系统	必要改动
Checkpointer
每 run 用独立 namespace，如 configurable.checkpoint_ns = run_id；结束后再合并状态
Sandbox
run 级 workspace 子目录或文件锁，避免并发写同一文件
ThreadState / messages
不能多 writer 无协调；需 run-scoped 输出，再 reconcile 到 thread
RunDispatcher
去掉 per-thread 串行限制，或新增 multitask_strategy: "parallel"
Gateway / join
多 run 同时 active 时的 stream/join 语义
前端
多路 SSE、多条 AI 气泡按 run_id 绑定；queued run 开始执行时的订阅逻辑
文档位置：docs/notes/task驱动/多轮对话/thread_run_queue_workers_20298d67.md 的 Phase 3 表格；T1-多任务.md 也提到「默认排队，可选开启并行 worker（Ultra/子任务模式）」——后者目前尚未实现。

5. 若暂时不想大改，可用的替代方案
方案	效果
enqueue（现状）
可连发，同 thread 串行执行
multitask_strategy: interrupt
新消息打断旧 run，立刻跑新的（不排队）
多开聊天 tab
不同 thread_id，天然并行（受全局 4 worker 限制）
一条消息 + 子代理 task
单 run 内多任务并行
一句话：两条消息在同一聊天里是 排队串行；不同聊天可以并发（最多约 4 个 run）；同聊天多条同时跑 需要 checkpoint/sandbox/前端一整套改造，当前未实现。

若要落地同 thread 并行，可以说一下更倾向「Ultra 模式开关」还是「新 API 策略 parallel」，我可以按现有代码结构拆一版改造步骤（Ask 模式下只能给方案，改代码需切 Agent 模式）
