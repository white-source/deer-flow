# DeerFlow 多轮协作二期 - 架构时序设计

> 这份文档记录的是完整二期多轮协作方案，不是一期 approval-only 的增量补丁。
> 它对应的目标是：运行中的 Agent 可以持续接收用户反馈、改写任务方向、切换前后台任务，并在同一 thread 内维持可解释的执行轨迹。

---

## 1. 设计结论

### 1.1 从 thread-owned runtime 升级为 run-owned runtime

当前 DeerFlow 的运行时主语仍然是 `thread`：

- 同一 `thread` 下 run 串行排队
- checkpoint 默认绑定 thread 根 namespace
- 前端默认一个 thread 只存在一条主流式执行链

这套模型适合「一个消息触发一个完整任务」，不适合「运行中插话、改计划、继续执行」。

二期要完成真正的多轮协作，必须把执行所有权提升到 `run / task / revision` 级别：

- `thread` 负责承载会话、消息历史、run 列表
- `run` 负责承载一个任务的生命周期
- `revision` 负责承载任务被用户中途改写后的版本边界

### 1.2 同一 thread 允许多 run，但不是多条主舞台平权刷屏

推荐采用：

- `1 foreground + N background`

含义：

- 一个 thread 同时允许多个 run 存在
- 任何时刻只有一个 foreground run 作为当前主交互对象
- 其他 run 可以后台继续执行，但不抢主流输出位

这样既支持“用户同时跑多个任务”，又不会把前端变成多路 token 流互相打架的终端监视器。

### 1.3 运行中插话不是原地修改，而是 fork 新 revision

用户在运行中说：

```text
别继续原计划，先做 A
```

这不是给旧 run 打一个字段补丁，而是：

1. 定位当前 active revision
2. 基于旧 revision 的 checkpoint 创建新 revision
3. 新 revision 继承已有上下文，但拥有新的执行轨迹
4. 前端将 active run 切换到新 revision
5. 旧 revision 进入 `superseded`、`paused` 或其他非活跃状态

这样才能保证：

- 执行轨迹可解释
- 调试和回放可落地
- 用户知道“为什么任务方向突然变了”

### 1.4 foreground 必须拥有更高调度优先级

如果 foreground 和 background 平等抢资源，系统虽然“更并发”，但用户眼前最关注的那条任务会更卡。

所以调度层必须承认产品层的 foreground / background 区分：

- foreground run 优先占用模型调用配额
- foreground run 优先占用工具执行配额
- background run 可以限速、延后、低优先级执行

这不是体验优化，而是产品契约的一部分。

## 2. 关键对象

### 2.1 Thread

线程只保留容器职责：

- 消息历史
- run 列表
- 当前 active run 指针
- 前端页面承载对象

thread 不再是唯一执行锁，也不再承担“恢复目标”的语义。

### 2.2 Root Run

一个用户任务的根对象。

例如：

```text
帮我分析这个月话费为什么上涨
```

这会创建一个 root run，例如 `R1`。

### 2.3 Revision

当 root run 在执行中被用户改写方向时，系统不原地覆盖，而是生成新 revision。

例如：

```text
R1      原始任务
R1.1    用户插话后产生的新版本
R1.2    再次重定向后的版本
```

revision 是真正的执行单元，也是 checkpoint、resume、inject、approval 的目标对象。

## 3. 主链路时序

### 3.1 创建 foreground run

```text
User
  -> Frontend
  -> Gateway API
  -> Run Registry: create root run R1
  -> Scheduler: assign R1 as foreground
  -> Worker(R1): start
  -> Checkpoint Store: load checkpoint namespace for R1
  -> Event Bus: publish run_started(R1)
  -> Frontend: activeRun = R1
```

此后前端渲染的是 foreground run 的主流输出。

### 3.2 在同一 thread 内再创建 background run

```text
User
  -> Frontend
  -> Gateway API
  -> Run Registry: create root run R2
  -> Scheduler: assign R2 as background
  -> Worker(R2): start
  -> Event Bus: publish background_started(R2)
  -> Frontend: run list update only
```

这里的关键点：

- `R2` 不再通过旧的 thread FIFO 排队等待
- `R2` 可以后台跑
- 但它不会抢占 `R1` 的主交互流

### 3.3 对 foreground run 插话并生成新 revision

```text
User: “别继续原计划，先做 A1”
  -> Frontend
  -> POST /runs/R1/inject
  -> Gateway API
  -> Run Registry: resolve active revision of R1
  -> Run Registry: create fork revision R1.1 (parent=R1)
  -> Scheduler: supersede old active revision
  -> Scheduler: promote R1.1 as new foreground
  -> Event Bus: publish revision_created(R1 -> R1.1)
  -> Frontend: activeRun = R1.1
```

旧 revision 不应继续被解释为“当前正在做的事”。

旧 revision 可以进入：

- `superseded`
- `paused`
- `background`

但不应该继续冒充 active revision。

### 3.4 新 revision 从旧 checkpoint 基础上继续执行

```text
Scheduler
  -> Worker(R1.1): start
  -> Checkpoint Store: load fork base checkpoint from R1
  -> Worker(R1.1): replan with injected instruction
  -> Sandbox / Tools / Model
  -> Checkpoint Store: append checkpoint for R1.1
  -> Event Bus: publish token/tool/state events for R1.1
  -> Frontend: render active stream of R1.1
```

这一步是整个设计的核心价值：

- 不是“结束旧任务，再从零启动一个新任务”
- 而是“继承旧上下文，但拥有新的执行轨迹”

## 4. 审批与恢复子链路

完整二期里，审批不是独立于 run revision 的另一套机制，而是 revision 生命周期的一部分。

```text
Worker(active revision)
  -> Tool call requested
  -> Sandbox / Tool layer returns approval required
  -> Checkpoint Store: persist pause checkpoint(revision)
  -> Run Registry: set status = awaiting_action
  -> Event Bus: publish tool_approval_requested(revision)
  -> Frontend: show approval card

User approves
  -> Frontend
  -> POST /runs/{revision}/resume
  -> Gateway API validates revision state
  -> Scheduler resumes revision as foreground
  -> Worker loads checkpoint
  -> Continue tool execution
```

如果用户不是批准，而是：

```text
“这个工具不要执行，改成先查另外一个方向”
```

那路径应当直接转向：

- `inject -> fork new revision`

而不是把 redirect 逻辑继续堆进旧 revision 的内部分支里。

## 5. 组件职责边界

### 5.1 Gateway API

负责：

- `create run`
- `resume revision`
- `inject / fork revision`
- `switch foreground`

不负责：

- 在一个万能 `start_run()` 里混合 create、resume、inject 的所有语义

二期应拆出明确接口，而不是继续扩展现有 create API 的 body 字段。

### 5.2 Run Registry

负责：

- root run / revision 元数据
- parent / supersedes / active revision 关系
- run 状态机

这是 run-owned runtime 的事实来源。

### 5.3 Scheduler

负责：

- foreground / background 策略
- 资源优先级
- revision 切换后的调度
- 多 run 并存时的配额控制

二期如果成立，这一层要替换掉当前的 `ThreadRunQueue + RunDispatcher` 外壳，而不是在旧抽象上补状态。

### 5.4 Event Bus / Stream Hub

负责：

- run 粒度事件流
- active run 切换通知
- background progress 更新
- revision timeline 事件

事件不再天然绑定“一个 thread 一条主 SSE 流”。

### 5.5 Frontend

前端模型要从：

- `thread + queued runs + join current stream`

升级为：

- `run list + active run + revision timeline`

主视图显示 foreground run，后台 run 只更新列表和状态。

## 6. 数据与隔离要求

### 6.1 Checkpoint namespace

旧模型使用 thread 根 namespace：

```text
thread_id + checkpoint_ns = ""
```

二期不应继续这样做。

推荐至少提升到 revision 级：

```text
run:{root_run_id}:rev:{revision_id}
```

否则会出现：

- 多 run 状态串线
- fork revision 恢复到错误上下文
- background run 覆盖 foreground run 的执行轨迹

### 6.2 Sandbox / Tool side effects

如果 checkpoint 已经 run-owned，但 sandbox 仍然 thread-owned，那么状态层面看起来是隔离的，副作用层面仍可能互相污染。

因此完整二期至少要明确：

- 当前是否接受“状态隔离先行，副作用隔离后补”
- 还是同步推进 run 级 workspace / side-effect 隔离

如果资源有限，建议在文档里明确分期，而不是让实现层隐含承担这个风险。

---

## 7. 为什么旧 dispatcher / queue 不值得继续保留

当前的 `ThreadRunQueue` / `RunDispatcher` 解决的是：

- 同一 thread 串行
- 后续 run FIFO 排队
- 前一个 run 结束后 drain 下一条

但完整二期的目标已经变成：

- run-owned lifecycle
- 同一 thread 多 run 共存
- foreground / background 并存
- inject 触发 revision fork

所以这不是“旧设计稍微不够用”，而是“旧设计的主语已经不对”。

因此建议：

- 不保形兼容旧 dispatcher
- 不继续扩展 thread queue 语义
- 二期直接引入新的 runtime coordinator / scheduler

旧实现可以保留在迁移期作为兼容路径，但不应该继续作为二期主架构。

---

## 8. 推荐落地顺序

### 阶段 A：先把对象边界改对

1. 引入 root run / revision 元模型
2. 引入 active revision 指针
3. 把 resume / inject / fork API 拆开

### 阶段 B：替换运行时外壳

1. 以 run-owned scheduler 替代 thread queue / dispatcher
2. 引入 foreground / background policy
3. 引入 revision 切换事件

### 阶段 C：升级前端心智模型

1. `run list + active run`
2. revision timeline
3. background run 状态展示

### 阶段 D：补隔离与观测

1. revision 级 checkpoint namespace
2. side-effect / sandbox 隔离策略
3. run timeline / event tracing / debug 视图

---

## 9. 一句话总结

这次改造的本质，不是“给现有 run 加一个 inject 接口”，而是把 DeerFlow 从：

```text
thread 驱动的串行任务系统
```

升级为：

```text
run / revision 驱动的持续协作系统
```

只要这个主语不改，对话中途插话、重规划、多任务前后台并存这些能力都会退化成各种特殊 case；主语一旦改对，审批、恢复、注入、切换前后台才会收敛成同一套运行时模型。
