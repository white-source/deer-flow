# DeerFlow → 多轮对话 Agent 改造计划

## Context

**目标**：将 deer-flow 从「任务驱动、单 run = 完整 ReAct loop」的执行模型改造为「对话驱动、每步可见可干预」的多轮持续对话 Agent（类似 Claude Code）。

**核心差距**：

| 维度 | 当前 deer-flow | 目标 (Claude Code 风格) |
|------|-------------|---------------------|
| 执行粒度 | 一个 Run = 完整 ReAct loop（模型→工具→模型→...→最终文本） | 每个决策步骤独立、用户可见 |
| 工具调用 | 在内部循环中静默执行 | 展示给用户，可审批/拒绝/重定向 |
| 轮次边界 | Run 开始→结束 | 对话持续进行，无"Run 完成"概念 |
| 用户干预 | 只能取消整个 Run | 审批工具、拒绝、重定向、追问 |

**推荐方案**：Hybrid Approach（方案 C）—— 保持 LangGraph `create_agent` graph 不变，使用 `interrupt_before=["tools"]` 暂停执行 + 新增 step_mode API 层。最大化复用现有基础设施（checkpointer、summarization、memory、StreamBridge、RunDispatcher、middleware 链），最小化增量改动。

### 1.3 修改 `run_agent()` — 捕获 GraphInterrupt

**文件**: `backend/packages/harness/deerflow/runtime/runs/worker.py`

关键改动点（第 275-334 行区域）：

1. **step_mode 自动设置 interrupt_before**：
   - 从 `config["configurable"].get("step_mode")` 读取
   - 如果 `step_mode=True`，自动设置 `agent.interrupt_before_nodes = ["tools"]`

2. **捕获 GraphInterrupt**（核心逻辑）：
   在 `agent.astream()` 的 try/except 中添加：
   ```python
   except GraphInterrupt as interrupt:
       # Graph 在 interrupt_before=["tools"] 处暂停
       pending_calls = _extract_pending_tool_calls(interrupt)
       await run_manager.set_status(run_id, RunStatus.awaiting_action)
       await bridge.publish(run_id, "tool_approval", {
           "pending_calls": pending_calls,
           "checkpoint_ns": interrupt.checkpoint_ns,
       })
       await bridge.publish_end(run_id)
       return  # 退出 run task，但保持 RunRecord 存活
   ```

3. **finally 块修改**：
   - 状态为 `awaiting_action` 时不设置 thread_meta 为 idle
   - 不调用 `notify_run_terminal`（让 dispatcher 不排空队列）
   - bridge cleanup 延时更长（如 300s），给用户决策留时间

### 1.4 新增 `resume_agent()` 函数

**文件**: `backend/packages/harness/deerflow/runtime/runs/worker.py`（新增函数）

```python
async def resume_agent(
    bridge, run_manager, record, *,
    ctx, agent_factory, config, stream_modes,
    resume_command: dict,  # {"action": "approve"|"reject"|"redirect", ...}
) -> None:
    """从 checkpoint 恢复被中断的 agent graph。"""
    # 重建 agent（与 run_agent 相同逻辑）
    agent = agent_factory(config=config)
    agent.checkpointer = ctx.checkpointer
    # ...
    
    # 使用 LangGraph Command 恢复
    from langgraph.types import Command
    cmd = Command(resume=resume_command)
    
    # 从被中断的 checkpoint 继续 stream
    async for chunk in agent.astream(cmd, config=config, stream_mode=...):
        # 与 run_agent 相同的 streaming 逻辑
        # 可能再次遇到 GraphInterrupt（新一轮工具调用）
```

### 1.5 StreamBridge 新增事件类型

### 1.6 RunManager 处理 `awaiting_action` 状态

**文件**: `backend/packages/harness/deerflow/runtime/runs/manager.py`

## Phase 3: 持久上下文 & Session 模型

### 3.1 消除 "Run 完成" 边界

**文件**: `backend/packages/harness/deerflow/runtime/runs/worker.py`

step_mode 下：
- run 只在以下情况真正结束：
  - 模型产出纯文本（无工具调用）→ `RunStatus.success`
  - 用户主动 cancel → `RunStatus.interrupted`
  - 超时 / 错误 → `RunStatus.error` / `RunStatus.timeout`
- `awaiting_action` 不是终止状态，是新消息无需创建新 run（可直接通过 resume 继续对话）
- 如果用户在 `awaiting_action` 时发送新消息，自动 reject 当前待审批工具 + 注入新消息

### 3.2 Thread meta 状态扩展

**文件**: `backend/packages/harness/deerflow/persistence/thread_meta/model.py`

`thread_meta.status` 新增可能值：
- `"awaiting_action"` — 有 run 在等待用户审批工具
- `"idle"` — 无活跃 run，可以开始新对话轮次
- `"running"` — agent 正在执行（可能正在思考或执行工具）

### 3.3 复用现有机制（无需改动）

- **Checkpointer**: 已持久化完整对话状态，step_mode 下 checkpoint 包含被中断的状态
- **Summarization middleware**: 已在 context 超限时自动压缩，step_mode 下继续工作
- **Memory middleware**: 已在每次 exchange 后提取记忆，step_mode 下继续工作
- **StreamBridge**: 已解耦生产者和消费者，新增事件类型即可

### 4.1 新增 `useConversationStream()` Hook

**新文件**: `frontend/src/core/conversation/hooks.ts`

```typescript
export function useConversationStream(options: ConversationStreamOptions) {
  // 基于现有 useThreadStream()，增加 step_mode 感知
  
  const [pendingApproval, setPendingApproval] = useState<PendingApproval | null>(null);
  
  // 监听 "tool_approval" 自定义事件
  // 暴露 approve / reject / redirect 函数
  
  const approve = useCallback(async () => {
    await apiClient.post(`/api/threads/${threadId}/runs/${runId}/resume`, { action: "approve" });
  }, []);
  
  const reject = useCallback(async (reason: string) => {
    await apiClient.post(`/api/threads/${threadId}/runs/${runId}/resume`, { action: "reject", rejection_reason: reason });
  }, []);
  
  const redirect = useCallback(async (modifications: ToolCallModification[]) => {
    await apiClient.post(`/api/threads/${threadId}/runs/${runId}/resume`, { action: "redirect", modified_calls: modifications });
  }, []);
  
  return { ...stream, pendingApproval, approve, reject, redirect };
}
```

## Phase 5: 渐进迁移策略

### 5.1 Feature Flag

所有新行为由 `context.step_mode = True` 控制。不设置时系统行为完全不变。

### 5.2 分阶段推出

1. **Phase 1-2 (后端 only, feature-flagged)**：实现核心执行和 API，所有现有测试通过
2. **Phase 3 (前端 opt-in)**：前端增加 "交互模式" 开关，默认关闭
3. **Phase 4 (默认开启)**：充分测试后，新线程默认使用 step_mode
4. **Phase 5 (清理)**：移除旧的自主运行路径

### 5.3 向后兼容保证

- **Checkpointer 格式**：不变
- **已有 run**：旧 run 仍可列表、join、cancel
- **IM Channels**：继续使用自主模式，不受影响
- **DeerFlowClient**：嵌入式客户端继续工作，step_mode 可选
- **Middleware 链**：完全不变
- **Sandbox / Subagent / MCP / Skills**：完全不变
