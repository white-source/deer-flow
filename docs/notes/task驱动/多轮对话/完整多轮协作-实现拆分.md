# DeerFlow 多轮协作二期 - 实现拆分

> 这份文档承接《完整多轮协作-架构时序设计》，目标不是再次解释为什么要做，而是把完整二期拆成可执行的四个阶段：状态模型、后端、前端、迁移步骤。

---

## 1. 总体拆分原则

完整二期的本质不是“给当前 run 增加几个新接口”，而是把 DeerFlow 从：

```text
thread 驱动的串行执行系统
```

替换为：

```text
run / revision 驱动的持续协作系统
```

因此拆分顺序必须遵守两个原则：

1. 先改主语，再改行为
2. 先建立新对象和新状态，再替换旧调度，再升级前端心智模型

如果顺序反过来，比如先在前端做“多任务 UI”，或者先在后端往 `start_run()` 里继续塞 `inject/resume/checkpoint` 分支，最后得到的只会是更多兼容胶水，而不是新的运行时。

---

## 2. 阶段一：状态模型

这一阶段的目标是：先把系统里“谁在运行、谁可恢复、谁被 supersede、谁是当前 active”这几个事实表达清楚。

### 2.1 新对象边界

完整二期建议显式引入三层对象：

### A. Thread

职责：

- 承载消息历史
- 承载 run 列表
- 维护当前 `active_run_id` 或 `active_revision_id`

thread 不再代表唯一的执行链。

### B. Root Run

职责：

- 表示一个用户意图发起的任务根对象
- 聚合该任务后续所有 revision

建议字段：

```text
run_id
thread_id
created_by_message_id
status_summary
foreground_state
latest_revision_id
```

### C. Revision

职责：

- 表示某一时刻的具体执行版本
- 承载 checkpoint、resume、inject、approval 的真实目标

建议字段：

```text
revision_id
root_run_id
parent_revision_id
supersedes_revision_id
status
execution_mode
checkpoint_namespace
is_active
priority_class
```

### 2.2 核心状态枚举

建议把状态拆为两类，不要再试图用一个 `RunStatus` 承担所有语义。

### A. 执行状态

```text
pending
running
awaiting_action
paused
superseded
completed
cancelled
error
```

说明：

- `awaiting_action` 代表等待审批或明确用户决策
- `paused` 代表人为暂停但仍可恢复
- `superseded` 代表已被新 revision 接管，不应再当成当前主执行链

### B. 前后台状态

```text
foreground
background
hidden
```

说明：

- 这是 UI / 调度优先级语义
- 不要把它和执行状态揉成一个字段

### 2.3 必须新增的关系约束

建议在状态模型里明确以下约束：

1. 一个 `thread` 同一时刻最多只有一个 foreground revision
2. 一个 root run 同一时刻最多只有一个 active revision
3. 一个 revision 一旦进入 `superseded`，不能再被直接 resume
4. `inject` 不能原地修改旧 revision，只能产生新 revision

### 2.4 checkpoint namespace 升级

当前 thread 根 namespace 形式：

```text
thread_id + checkpoint_ns = ""
```

不再适合完整二期。

建议升级为 revision 级 namespace：

```text
run:{root_run_id}:rev:{revision_id}
```

如果不先改这件事，后续所有并发、多 revision、恢复路径都会有串线风险。

### 2.5 这一阶段的交付物

需要落地的成果：

- 新的 `run / revision` 数据结构
- 明确的状态机定义
- revision 级 checkpoint 命名规范
- thread / root run / revision 三者关系图

这阶段先不追求前端可见，只追求模型清晰。

## 3. 阶段二：后端实现

这一阶段的目标是：用新的 run-owned runtime 替换当前 thread-owned queue / dispatcher 语义。

### 3.1 不继续扩展旧 dispatcher / queue

当前：

- `ThreadRunQueue`
- `RunDispatcher`
- `per-thread serialization`

这些抽象编码的是：

```text
同一 thread 串行 + FIFO 排队
```

完整二期里，这套抽象应视为旧运行时外壳，而不是继续升级的基础。

建议新建运行时协调层，例如：

```text
RunCoordinator / RunScheduler / RevisionScheduler
```

它负责：

- foreground/background 调度
- revision 切换
- inject / fork 目标路由
- 配额优先级
- 生命周期收敛

### 3.2 API 层拆分

必须从“万能 create 路由”拆出来。

建议接口按动作分层：

### A. create

```text
POST /threads/{thread_id}/runs
```

语义：创建 root run

### B. resume

```text
POST /runs/{revision_id}/resume
```

语义：恢复一个处于 `awaiting_action` 或 `paused` 的 revision

### C. inject

```text
POST /runs/{revision_id}/inject
```

语义：在当前 revision 基础上生成新 revision

### D. switch foreground

```text
POST /threads/{thread_id}/active-run
```

语义：切换 thread 的前台 run / revision

### 3.3 Registry 层

后端需要一个统一的元数据事实来源，而不是把一半状态放在 manager，一半状态靠前端猜。

建议负责：

- root run 创建
- revision 创建 / supersede
- active revision 查询
- revision 可恢复性校验
- thread 当前 foreground 指针维护

### 3.4 Worker 层

worker 不再假设“一个 run 从创建走到终态就是完整生命”。

需要支持：

1. 以 revision 为单位启动
2. 从指定 revision checkpoint 恢复
3. 被 supersede 时收敛旧 revision
4. 在 approval / pause / inject 场景下交还控制权

### 3.5 事件层

当前事件模型默认是“一个 thread 对应一条主 stream”。

完整二期需要把事件提升到 run / revision 级：

- `run_created`
- `revision_created`
- `active_revision_switched`
- `foreground_started`
- `background_progress`
- `tool_approval_requested`
- `revision_superseded`
- `revision_completed`

### 3.6 调度优先级

调度器至少要支持：

1. foreground 优先于 background
2. background 可限速
3. foreground 切换后新 active revision 立即获得更高配额
4. 被 supersede 的旧 revision 不再继续消耗高优先级配额

### 3.7 后端阶段的最小可交付顺序

建议顺序：

1. 先引入 registry 和 revision 元模型
2. 再拆 API
3. 再替换 scheduler
4. 最后改 worker 和事件分发

不要先动 worker 再补 registry，否则你会到处传临时字段。

## 4. 阶段三：前端实现

这一阶段的目标是：让前端心智模型和新的后端语义一致，不再默认“一个 thread 只有一条 joinable stream”。

### 4.1 从 thread single-stream 升级为 run list + active run

当前前端主要假设：

- 当前 thread 正在加载
- 新消息要么直接提交，要么 enqueue
- 等 run 离开 queued 状态后 join 同一条 stream

这在完整二期不成立。

建议新模型：

### A. Thread 页面状态

```text
thread messages
run list
active run id
active revision id
background summaries
```

### B. 主视图

只展示 active run 的主流输出。

### C. 侧边视图 / 列表视图

展示：

- 其他 background run 的状态
- 当前 root run 的 revision timeline
- 是否存在 awaiting_action

### 4.2 输入框行为变化

发送消息时要先判断用户意图作用于谁：

1. 创建新 root run
2. 给当前 active revision 发 inject
3. 对 awaiting_action revision 发 resume / reject / redirect

也就是说，前端不能再把“用户输入”默认映射为“POST /threads/{thread}/runs/stream”。

### 4.3 revision timeline

当用户中途改变方向时，前端需要把这件事可视化。

至少应能看出：

```text
R1      原始任务
R1.1    由于用户插话而创建
R1.2    再次调整后创建
```

否则用户只会看到任务突然跳线，不知道发生了什么。

### 4.4 foreground / background 切换

前端需要支持：

- 切换当前 active run
- 只在 active run 上渲染主流 token 输出
- background run 只渲染状态更新和摘要

### 4.5 审批卡片目标必须绑定 revision

审批 UI 不能只知道 thread_id。

必须知道：

- 当前等待决策的是哪个 revision
- 用户点击 approve / reject / redirect 时请求打到哪个 revision

### 4.6 前端阶段的最小可交付顺序

建议顺序：

1. 先引入 run list + active run 状态容器
2. 再改输入框目标路由
3. 再加 revision timeline
4. 最后补 background 展示和通知

不要先做复杂 UI 动画，先把对象归属关系做对。

## 5. 阶段四：迁移步骤

这一阶段的目标是：把系统从旧 runtime 平滑迁到新 runtime，而不是一次性硬切导致所有线程与历史数据失效。

### 5.1 迁移原则

建议遵守：

1. 新旧运行时并存一段时间
2. 新能力对新建 run 生效
3. 老 thread 不强制立即迁移到 revision 模型

### 5.2 推荐迁移阶段

### Step A. 引入新对象但不开放新能力

动作：

- 添加 root run / revision 模型
- 新建 run 默认仍只创建一个 revision
- 暂时保持旧 dispatcher / queue 行为

目的：

- 先完成数据结构迁移
- 降低运行时替换难度

### Step B. 新接口可用，旧接口仍兼容

动作：

- create / resume / inject / active-run 新接口上线
- 旧 create 接口继续保留
- 服务层内部逐步改为使用 registry + revision 模型
- 通过 `DEER_FLOW_REVISION_RUNTIME_ENABLED` 开关控制 revision checkpoint namespace（开启后使用 `run:{root_run_id}:rev:{revision_id}`，关闭时保留 legacy namespace）

目的：

- 给前端和集成方留迁移窗口

### Step C. 新 scheduler 接管新线程

动作：

- 新建 thread 使用 run-owned scheduler
- 旧 thread 仍可留在旧 dispatcher 路径

目的：

- 缩小迁移爆炸半径

### Step D. 前端切到 run list + active run

动作：

- 默认页面使用新状态模型
- 旧的 enqueue/join helper 进入兼容层

目的：

- 完成产品心智切换

### Step E. 下线旧 dispatcher / queue

前提：

- 没有新流量再依赖旧 thread FIFO 模式
- run-owned scheduler 已覆盖主链路

动作：

- 删除 `ThreadRunQueue`
- 删除 `RunDispatcher` 主入口依赖
- 清理旧测试和旧前端 helper

### 5.3 风险控制项

迁移期重点关注：

1. checkpoint 兼容读取
2. 历史 thread 在 UI 中如何展示
3. 老 run 是否允许 resume
4. 旧 queued run 如何收敛到新 scheduler 语义
5. event schema 是否会破坏现有 stream consumer

### 5.4 迁移完成标志

可以认为完整二期迁移完成的标志：

1. thread 不再是唯一执行锁
2. inject 默认生成新 revision
3. 同一 thread 可同时存在 foreground + background run
4. 前端不再依赖 queued-join 单流逻辑
5. 旧 dispatcher / queue 从主路径退出

## 7. 一句话落地策略

最稳的落地方式不是：

```text
先把旧系统补到勉强能跑多轮，再慢慢重构
```

而是：

```text
先建立 run / revision 状态模型，再替换后端调度，再升级前端心智，最后下线旧 thread queue runtime
```

换句话说，完整二期不是“补功能”，而是一次受控的运行时换壳。
